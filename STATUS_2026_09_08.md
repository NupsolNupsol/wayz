## 6. New in this round: discount codes

Built on top of the list, at the client's suggestion.

**How it works.** The CEO opens **My company → Discount codes → New batch**: a name, how many codes,
the percentage, an optional expiry, and which activities the code works on. The platform mints that
many unique codes and they can be exported as a CSV to print or hand to a partner.

A customer reads a code out at any desk; the agent presses **Discount code** on the payment step,
types it in, and the percentage comes off the sale.

**The controls around it:**

- A code works **exactly once**. Two desks racing on the same code end with one discount and one refusal.
- Codes are checked for: ours, unused, in date, batch still live, and valid for that activity.
- Codes read cleanly off paper — no `O`, `I`, `0` or `1` in them.
- **Stop unused codes** kills every code still out there and leaves the spent ones on the record.
- Every redemption shows which booking it paid for, at which desk, by which agent.
- Only the CEO can mint or stop a batch. A desk agent cannot.

**Ready to test on the demo now** — two batches are seeded:

| Batch | Worth | Valid on | Example codes |
|---|---|---|---|
| Opening week | 25% | any activity | `WZ-4F7K2Q`, `WZ-9HTM3D`, `WZ-2BQX8N` |
| Lagoon summer | 50% | Lagoon only | `LAG-5TQ9WD`, `LAG-2HMK7B` |

## 7. Two other things fixed this round

- **A finished rental stops counting.** Reported while testing: a completed booking still showed a
  running overtime. The clock now stops where the session stopped, everywhere it is shown.
- **No typed amount can exceed what is owed.** The split-payment amount, the discount percentage and
  the visitors on a boat clamped only when you clicked away, so an impossible figure could be typed
  and quoted from. They hold their bounds as you type now.

## 7b. Found and fixed while re-testing the counter

Four more, all raised or uncovered during the same session:

- **A half-finished bag drop no longer disappears.** The Mobility and Lagoon counters kept a
  half-finished sale if the agent tapped away to another screen; **Shop & Drop did not**. It does
  now — customer, bags, plan and quote all come back, with a line saying the sale was picked up
  where it was left and a button to start fresh instead.
- **"Confirm the customer before taking their money" on a customer who *was* confirmed.** The box
  lets the desk send the code by WhatsApp **or email**. A code answered by email was never recorded
  as proof, so the box turned green and the payment was then refused. Fixed, and confirmed by
  running the old code against the new test: it reproduces the exact refusal, and the fix clears it.
- **The green "Customer verified" tick now expires** with the confirmation itself, so a proof that
  has quietly lapsed cannot look valid while the agent is taking money.
- **The discount code box reached Shop & Drop.** It was on the Mobility/Lagoon counter and the till
  queue but not on the bag counter, so a customer's code could not be taken there.

**Discounts in the books** were checked end to end, not assumed: the discount is a real line on the
order, the till's expected cash rises by the discounted amount and not the list price, the
accountant's ledger and the till transaction carry the same figure, the list price cannot be
charged afterwards, and the redemption is on the audit trail with who gave it and against what.

## 7c. Everything the customer reads is now in Arabic

Asked for after the afternoon round: the printed invoice, the emails and the WhatsApp messages had
to be Arabic, not English.

| What leaves the platform | Now |
|---|---|
| The auto-printed slip | Arabic, right to left, **whatever language the agent is working in**. The agent can run the platform in English and the customer still walks away with an Arabic invoice. |
| The lines on that slip | Arabic — the product's Arabic name, the bag count, the deposit, the discount and its reason, the overtime charge. The agent still sees the English names on their own screen. |
| Confirmation codes (WhatsApp) | Arabic. The code itself stays in Latin digits so it can be read out. |
| Confirmation codes (email) | Arabic, right to left, with the code shown left to right. |
| The invoice sent by WhatsApp | Arabic, with the amount, the reference and the tracking link. |
| "Your storage is nearly up" | Arabic, including the grace period and the hourly rate. |
| A new colleague's invitation email | Arabic, and the job title is named in Arabic too. |

Two notes, so nothing is a surprise on the day:

- **Names stay as they are recorded.** The company's registered legal name, the branch, the desk and
  the cashier print exactly as they are held in the company record — a tax invoice should carry the
  registered name, and we will not transliterate a person's name on your behalf. If you want those
  in Arabic on the slip, tell us and we will add Arabic names to the company, station and staff
  records.
- **Products carry their own Arabic name.** Every seeded product has one, and the product form has an
  Arabic-name field. A product created without one falls back to its English name on the slip — so
  fill that field in when you add a product.
- **Discount reasons now have an Arabic column** in Operating rules, because the reason is printed on
  the customer's copy. The English wording is used if the Arabic one is left empty.

**Verified by:** `npm run test:arabic` — **35 checks**, covering every message the platform sends and
every line of a real invoice (bags, discount, deposit, overtime), plus two browser tests that pay for
a rental with the interface in **English** and read the Arabic slip that comes out of the printer.

## 9. Two deployment settings to be aware of

Neither is a platform defect; both are environment settings on the server.

- **`PUBLIC_API_URL`** — WhatsApp fetches the invoice PDF from here. Without a reachable address the
  message still goes, as text with a link.
- **`PUBLIC_APP_URL`** — the customer tracking page printed on the invoice as a QR code. The dead
  `mallgo.nupsol.com/track/...` link in the WhatsApp reminder is this setting pointing at a domain
  that is not serving the web app.

One note on the printer: the platform sends the receipt to the printer by itself after every
payment. Whether the device shows a print dialog first is the browser's setting on that machine —
on the SUNMI, Chrome's kiosk-printing mode makes it silent.
